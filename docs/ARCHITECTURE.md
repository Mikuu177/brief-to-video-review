# 架构与审核原理

React + TypeScript前端由FastAPI同源提供。PostgreSQL保存项目、素材、版本、规则、阶段、证据和人工决定；Redis/RQ执行后台任务。原文件置于私有数据卷，供应商密钥只在后端。

## Brief

文件哈希 → 文件/页清单 → 独立受限进程读取 → 原生文字、OCR与区域分别保留 → 主单元与检测单元对账 → Markdown归档回查 → 人工处理未决区域 → 规则提取/确认/冻结。

G0/G1解决来源与读取记录，不宣称语义规则已全部提取。规范中的G2–G4字段是后续契约，不应将预留字段当已实现能力。见`BRIEF_G0_SPEC_v1.json`及`contracts/`。

## 脚本与视频

脚本依据被冻结的规则逐条给出候选，并核对来源引文。成片先对原片探测、完整音轨识别和内容观察，再处理连续重叠MP4片段，统一回到原片毫秒时基。解码帧清单用于工程对账，不冒充逐帧语义理解。

内容层将原始事实、实体身份和解释分开，利用全片、连续单元、专项、盲读和全局对账保留分歧。对悬空引用、未知时间或非法JSON保留原响应并在有限预算内恢复，不删除坏条目制造完成率。

视觉专项覆盖五类，两轮全片观察加疑似连续区间复核。没有品牌参考或范围无法确定时保留UNCERTAIN。只有候选证据和人类最终决定，不承诺自动判定所有主观画面质量。

## 版本与工作空间

素材哈希与规范/脚本/内容版本进入输入快照；修改产生新版本，旧记录保留并按依赖标记过期。阶段检查点可复用，远端状态不明时不会无限重发。

默认单用户模式仍使用内部`workspace`用户记录，保留数据库审计关联。它不提供身份隔离；可选session模式才验证账户与项目权限，API跨来源写请求检查始终保留。
